## Problem Statement

PR readiness is fragmented (§5 "PR readiness | Fragmentado"): `/create-pr`, Build, and Ship each hold an implicit, divergent notion of "ready" — Build's checklist, Ship's 6-item gate, and /create-pr's own conventions share no definition, mutable state (working tree, tests) is never revalidated at publication time, and the PR description is reconstructed by hand instead of reusing the evidence the workflow already produced (§14.2–14.3).

## Target Users

| ID | User | Role | Pain Point |
|----|------|------|------------|
| - | AgentSpec maintainer (Matheus) | Merges PRs | A PR opened hours after Ship may no longer reflect a passing state; descriptions are hand-rebuilt |
| - | Autopilot runs | PR is the terminal stage | No contract says what the PR stage may assume from Ship — it re-derives readiness ad hoc |
| - | Plugin consumers | Use /create-pr standalone | Without a PR_READY artifact, /create-pr has no evidence surface and no revalidation discipline |

## Goals

What success looks like (prioritized):

| ID | Priority | Goal |
|----|----------|------|
| REQ-001 | **MUST** | `pr_readiness` contract block (§14.1 dimensions): `branch` (working tree clean, base resolved), `quality` (lint / types pass-or-not-configured / tests / build), `traceability` (MUST requirements covered — the filled matrix), `review` (branch verdict ∈ {clean, clean-with-minors}, 0 open blocking findings), `delivery` (migration/rollback present-or-n/a, residual risks documented) — EACH item mapped to its existing evidence source (report sections, gate results, git state) |
| REQ-002 | **MUST** | `PR_READY_TEMPLATE.md` (new): the checklist filled with evidence pointers + the §14.3 description skeleton (problem/solution, scope, requirements delivered, test strategy, summarized matrix, residual risks, migration/rollback, review findings, validation instructions, screenshots-when-applicable) |
| REQ-003 | **MUST** | `sdd-ship` SKILL: after Gate S passes, validate `pr_readiness` from the archived evidence and write `PR_READY_{FEATURE}.md` to reports/; a failed dimension → gap report naming specific actions, no destruction, ship itself still completes (PR_READY is the extra artifact, not a new ship blocker) |
| REQ-004 | **MUST** | `/create-pr` command: consume the PR_READY artifact when present — revalidate the MUTABLE subset immediately before publication (working tree clean, tests green, branch verdict unchanged since ship) and generate the description from the artifact's skeleton (matrix pasted, never reconstructed); no PR_READY → legacy conduct preserved; publication ALWAYS requires explicit user intent (or the autopilot PR stage, which the user's flags already sanction) |
| REQ-005 | **MUST** | `sdd-build` boundary line: Build produces evidence, never opens PRs; `sdd-autopilot` PR stage consumes the PR_READY artifact |
| REQ-006 | **MUST** | Version bump + history |
| REQ-007 | **SHOULD** | Documental tests: block shape + evidence mapping, template sections, three consumers' anchors, explicit-intent guard |
| REQ-008 | **COULD** | PR_READY cleanup guidance (delete/archive after the PR URL exists) |

**Priority Guide:**
- **MUST** = MVP fails without this
- **SHOULD** = Important, but workaround exists
- **COULD** = Nice-to-have, cut first if needed

## Out of Scope

- New linter rules (the underlying evidence — matrix, verdicts, gates — is already linter-enforced; a PR_READY phase contract is a possible follow-up once adoption exists)
- Changing Gate S or the 6-item pre-ship checklist (PR_READY generation happens AFTER the gate, additively)
- Auto-merge or merge-strategy automation (maintainer's decision, §13)
- Replacing the GitHub provider or publishing without intent (§21)
- Increment 9
