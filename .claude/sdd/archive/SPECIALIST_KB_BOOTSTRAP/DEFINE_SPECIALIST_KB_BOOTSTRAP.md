# DEFINE: Specialist KB Bootstrap

> Generated specialist agents are born with a light, source-validated KB — created by kb-architect on its own (non-main-loop) model before the first delegation — and light KBs get promoted to `--validated` when reuse proves the domain matters.

## Problem Statement

A specialist agent generated by the provisioning flow operates ungrounded (`kb_domains: []`) whenever its domain has no KB — the A-003 risk of SPECIALIST_AUTOPROVISION was shipped as accepted — and nothing ever promotes an auto-generated light KB to validated status, so bootstrap-quality grounding becomes permanent by default.

---

## Target Users

| User | Role | Pain Point |
|------|------|------------|
| Autopilot operator (Matheus) | Runs `/auto` intention-driven, lights-out | Generated specialists execute with zero domain grounding; KB quality never improves without manual intervention |
| Supervised SDD user | Runs `/design` + `/build` interactively | Manual `/create-kb` detour to ground a just-generated specialist, then a second manual pass to validate it |

## Goals

What success looks like (prioritized):

| Priority | Goal |
|----------|------|
| **MUST** | KB bootstrap on agent provisioning: when the layer gate lands on AGENT and the domain is absent from `_index.yaml`, the agent is created already declaring `kb_domains: [domain]` and the manifest gains a "create KB" task (`@kb-architect`, light mode + mandatory source validation, `genai` as few-shot shape) dependency-ordered **before** the specialist's tasks |
| **MUST** | Provenance header on every generated KB file — auto-generated marker, date, cited sources, confidence, "review before promoting to ground truth" note; the header doubles as the "unvalidated" sensor |
| **MUST** | Bounded degradation: KB-task failure (after Gate B retries) reverts the agent to `kb_domains: []`, regenerates the router, records a WARN — the run never aborts because of a KB task |
| **MUST** | Zero new machinery: the KB task is governed by the existing Gate B; model policy lives only in kb-architect's frontmatter (`model: sonnet` — never the main-loop model); Gate P and `WORKFLOW_CONTRACTS.yaml` untouched |
| **SHOULD** | Reuse-triggered promotion: a run that delegates to an agent whose KB is marked unvalidated appends the `--validated` upgrade (`kb-build`) as its **final best-effort task** — failure → WARN, never a blocker |
| **SHOULD** | Provenance rows: every KB creation and upgrade event recorded in the RUN REPORT / BUILD_REPORT |
| **COULD** | Bootstrap summary in the DESIGN document (which domains got bootstrapped KBs in this run) |

**Priority Guide:**
- **MUST** = MVP fails without this
- **SHOULD** = Important, but workaround exists
- **COULD** = Nice-to-have, cut first if needed

## Success Criteria

Measurable outcomes (must include numbers):

- [ ] 100% of generated **agents** whose domain lacks a KB get a light + source-validated KB created by `@kb-architect` as a manifest task ordered before the specialist's first task (0 first delegations without the KB on disk, except the declared degradation path)
- [ ] 100% of generated KB files carry the provenance header; 0 generated KB files indistinguishable from hand-validated ones
- [ ] 0 runs aborted because of a KB task: failure path reverts to `kb_domains: []` + router regeneration + WARN in 100% of failure cases
- [ ] 100% of runs that delegate to an unvalidated-KB agent append the `--validated` upgrade as the final best-effort task
- [ ] 0 duplicate KB creations for the same domain within a run; `_index.yaml` registration strictly additive (0 overwrites)
- [ ] 100% of KB creation and upgrade events have a provenance row
- [ ] 0 new gates, 0 new config surfaces, 0 changes to `WORKFLOW_CONTRACTS.yaml`

## Acceptance Tests

| ID | Scenario | Given | When | Then |
|----|----------|-------|------|------|
| AT-001 | Domain already has a KB | An agent gap in a domain present in `_index.yaml` | The provisioning sub-flow creates the agent | `kb_domains: [domain]` cites the existing KB; no KB task is added |
| AT-002 | Domain lacks a KB | An agent gap in a domain absent from `_index.yaml` | The provisioning sub-flow creates the agent | Agent declares `kb_domains: [domain]`; the manifest gains a KB task ordered before every task assigned to the new specialist |
| AT-003 | KB task executes | A manifest with a KB task | `sdd-build` reaches it | `@kb-architect` runs on its frontmatter model (not the main-loop model), produces a `genai`-shaped KB with the provenance header on every file, registers it additively in `_index.yaml`; only then do the specialist's tasks run |
| AT-004 | KB task fails | KB task exhausts Gate B's 3 retries | The build continues | Agent reverted to `kb_domains: []`, router regenerated, WARN provenance row written; the specialist's tasks still execute (status-quo grounding) |
| AT-005 | Reuse triggers promotion | A run delegates to an agent whose KB carries the unvalidated provenance marker | The manifest is assembled | The `--validated` upgrade (`kb-build`) is appended as the run's final task, best-effort: success flips the header to validated; failure records WARN and the light KB remains |
| AT-006 | Same domain twice in one run | A second gap (or reuse) for a domain whose KB was created earlier in the same run | Resolution runs | The just-created KB is cited; 0 duplicate creations |
| AT-007 | Generated skill (scope boundary) | The layer gate lands on SKILL for a gap | The provisioning sub-flow completes | No KB task is created — KB bootstrap applies to generated agents only |
| AT-008 | Provenance recorded | Any KB creation or upgrade event completed | The RUN REPORT / BUILD_REPORT is written | It contains a row for the event (domain, mode light/validated, trigger, outcome) |

## Out of Scope

Explicitly NOT included (all confirmed in the brainstorm; auto-upgrade was pulled back into scope by the user with the reuse trigger and is NOT in this list):

- Backfilling KBs for the 58 existing agents' uncovered territories
- Judge/eval pass over generated KBs (Judge V1+ territory)
- Refreshing stale existing KBs during provisioning
- Rollout of generated KBs to vendored consumer repos (owned by `rollout-agentspec`)
- New model-override configuration surface for KB tasks

## Constraints

| Type | Constraint | Impact |
|------|------------|--------|
| Technical | No new gates: Gate B governs the KB task; Gate P and `WORKFLOW_CONTRACTS.yaml` remain untouched | The KB task must behave as an ordinary manifest task, including its failure semantics |
| Technical | Single-source reuse: `/create-kb` light mode, `kb-build`, `kb-architect`, and the `specialist-autoprovision` sub-flow are extended, never restated | New logic lands only in the sub-flow extension and one reuse-detection hook |
| Technical | Model policy lives only in kb-architect's frontmatter — subagent delegation natively runs the declared model | "Non-Fable" requirement satisfied with zero configuration |
| Technical | `_templates/` are the binding KB structure; `genai` is the few-shot shape target; `_index.yaml` registration strictly additive | The KB task prompt must reference both; no invented structures |
| Security | Public-repo hygiene: generated KB content passes the same blocking private-context grep as generated components | Hygiene gate runs before the KB lands, never after |
| Process | Never-worse-than-status-quo invariant (inherited): every failure path terminates at today's shipped behavior, loudly | No failure mode may abort the run or leave a broken `kb_domains` reference |

## Assumptions

Assumptions that if wrong could invalidate the design:

| ID | Assumption | If Wrong, Impact | Validated? |
|----|------------|------------------|------------|
| A-001 | A light KB produced in a single kb-architect pass with mandatory source validation is net-positive grounding versus no KB | Generated KBs mislead specialists with authoritative-looking errors — would need `--validated` at birth or the deferred judge pass | [ ] |
| A-002 | Reuse (a later run delegating to the domain) is a reliable promotion signal | Rarely-reused domains keep light KBs forever — acceptable; manual `/create-kb --validated` remains available | [ ] |
| A-003 | The 6-stage `--validated` build fits as a final best-effort task without wrecking run duration | Upgrade moves to a post-run queue or a scheduled maintenance flow | [ ] |
| A-004 | The provenance header is a reliable machine-readable "unvalidated" sensor | Would need an explicit validation field in `_index.yaml` (additive schema change decided at Design) | [ ] |
| A-005 | kb-architect respects `_templates/` + the `genai` shape from prompt instructions alone in a single pass | KB task verification gains a template-conformance check (structure diff against `_templates/`) | [ ] |

**Note:** Validate critical assumptions before DESIGN phase. Unvalidated assumptions become risks.
