## Summary

PR readiness is now a shared contract instead of tribal knowledge: the `pr_readiness` block (v3.15.0) names 13 items across branch/quality/traceability/review/delivery dimensions, each mapped to evidence the pipeline already produces (BUILD_REPORT sections, the filled Traceability Matrix, review verdicts) with an explicit `mutable:` split. Ship validates the checklist after Gate S and generates a PR_READY artifact (new template: checklist + §14.3 description skeleton + Gaps); `/create-pr` consumes it — skip-gate over its legacy analysis steps, mutable-subset revalidation immediately before publication, description pasted never rebuilt. Build's boundary is now written down: it produces evidence and never opens PRs; publication always requires explicit user intent. Zero linter changes by design — every checklist item's evidence was already linter-enforced by Increments 1–7. Increment 8 / PR 8; seventh autonomous /auto run, and the first whose ship phase dogfoods its own deliverable (the PR_READY artifact driving PR 8 itself).

## Lessons Learned

### Process

- Dogfooding closes the loop fastest: this increment's own PR is the first consumer of the artifact it built — any friction in the checklist or skeleton surfaces immediately, on the author's own PR.
- A fix can introduce the next finding: the F5 "close-run commit" wording referenced a commit no stage defined — the reviewer probing the fix (not the original defect) caught it. Budget follow-through time for fixes-of-fixes.

### Technical

- Evidence must point at sections that exist: two checklist items initially cited phantom anchors ("delivery notes", an unanchored re-review claim). Contract evidence strings deserve the same existence-check discipline as code references — the reviewer's anchor-existence grep is the pattern to keep.
- `X/N` grammar is load-bearing: the build gate FAILed this increment's own report for a chatty "1/2 (plus …)" fix-rounds value — Increment 1's strict parser doing exactly its job on its author.
