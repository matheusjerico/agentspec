## PR Description (generated — paste, don't rebuild)

### Problem & solution

The program produces rich evidence (matrices, verdicts, fix rounds, gate ledgers) but no comparable numbers: answering "did rigor go up and defects go down between run A and run B?" meant reading two BUILD_REPORTs end to end. This PR adds a versioned machine-readable `workflow_metrics` block (schema v1) to every BUILD_REPORT — emitted by Build from measured values only, validated by five new linter rules, summarized by Ship. The availability rule is the spine: an unmeasured value is `{value: null, reason}` — never estimated, interpolated, or copied from a prior run — and the linter enforces it mechanically, down to rejecting a verbatim unfilled template copy.

### Scope & out of scope

**In scope:** the contract block (WORKFLOW_CONTRACTS.yaml v3.16.0 — closed 13-key catalog per plan §15.1), BUILD_REPORT template emission skeleton, SHIPPED template summary subsection, sdd-build/sdd-ship conduct, 5 `BR.metrics_*` rules built TDD RED-first (21 unit tests), 10 documental anchors.
**Out of scope (explicitly):** adaptive automation of any kind — metrics never auto-change policies; risk recalibration requires multiple comparable runs AND human review (§15.3). Also excluded: telemetry upload, token/cost estimation, and the §22 benchmark repetition itself (this builds the measuring stick, not the experiment).
